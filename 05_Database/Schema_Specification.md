# Creator OS Foundry Schema Specification

**Phase:** 1.2 — Database Implementation Layer  
**Version:** 1.0  
**Document owner:** Data Owner  
**Status:** Proposed  
**Risk class:** High

## Purpose

This document specifies the initial physical PostgreSQL conventions and table contracts for Creator OS Foundry. It implements the [Database Model](Database_Model.md) while preserving room for reviewed migrations.

## Scope

This specification covers identifiers, common columns, schemas, entity tables, relationships, constraints, indexing, events, and data lifecycle. Exact SQL will be delivered through approved migrations.

## Global Conventions

- Use lowercase snake_case for schemas, tables, columns, indexes, constraints, and functions.
- Use UUID primary keys generated by an approved database default.
- Store timestamps as timestamptz in UTC.
- Every workspace-owned mutable record must include id, workspace_id, status, created_at, updated_at, created_by, updated_by, and version.
- Use explicit foreign keys and named constraints.
- Use text plus check constraints or governed lookup tables for controlled states; native enums require explicit migration review.
- Money must use numeric with an explicit currency code. Never use floating-point types for currency.
- Secret values must not be stored in ordinary tables. Store only protected credential references.
- JSONB is permitted for bounded, versioned extension data, not as a substitute for modeled relationships.
- Material state changes must emit append-oriented events.

## Schema Layout

| Schema | Purpose | Exposure |
| --- | --- | --- |
| public | Approved application-facing relations | Data API only with grants and RLS |
| internal | Privileged helpers, operational tables, and protected lookups | Not exposed |
| audit | Append-oriented events and security evidence | Not exposed |
| reporting | Approved read models and security-invoker views | Explicitly controlled |
| auth | Supabase-managed identity objects | Platform managed |
| storage | Supabase-managed object metadata | Platform managed |

### Audit

The audit.events table must include event_id, workspace_id, event_type, aggregate_type, aggregate_id, actor_type, actor_id, request_id, occurred_at, schema_version, classification, and payload. Ordinary application roles must not update or delete audit events.

## Relationships and Delete Behavior

Foreign keys must state delete behavior explicitly. Use restrict by default for governed records. Cascade is permitted only for strictly dependent, non-audit children with documented retention behavior. Identity deletion must not erase required approvals, decisions, incidents, usage, or audit evidence; use lifecycle status and privacy-approved pseudonymization where necessary.

## Indexing Requirements

- Index every foreign key used for joins or policy checks.
- Create composite indexes beginning with workspace_id for common tenant-scoped access paths.
- Add partial indexes for active or queued records when evidence supports the query.
- Keep policy predicate columns indexed.
- Require query-plan evidence before adding specialized indexes.
- Review unused, overlapping, and high-write-cost indexes before release.

## Concurrency and Time

Updates must increment version or enforce an equivalent optimistic concurrency check. Use database-generated timestamps for canonical creation and update time. Scheduled work must record timezone separately when local-time meaning matters.

## Views and Functions

Views exposed to application roles must use security-invoker behavior on supported PostgreSQL versions or remain in an unexposed schema. Functions use security invoker by default. A security-definer function requires documented necessity, a protected schema, fixed search_path, explicit execute grants, internal authorization checks, and Security Owner approval.

## Acceptance Criteria

- Every conceptual entity maps to a table or documented deferred decision.
- Workspace ownership and lifecycle fields are consistent.
- Foreign keys, uniqueness, checks, delete behavior, and indexes are explicit.
- Audit and credential data receive stricter controls.
- The specification can be represented by reversible, tested migrations.
