# Creator OS Foundry Documentation Data Model

**Phase:** 2.2 — Documentation Engine Implementation  
**Version:** 1.0  
**Document owner:** Documentation Steward and Data Owner  
**Status:** Proposed  
**Risk class:** Moderate

## Purpose

This document defines the implementation data model for the Documentation Engine. GitHub-tracked Markdown is the canonical content store. Supabase stores governed metadata, lifecycle state, provenance, workflow records, audit events, and rebuildable discovery artifacts.

## Scope

The model covers document identity, versions, sources, relationships, reviews, approvals, validation, publication, synchronization, and indexing. It does not move canonical prose out of GitHub or store secrets in documentation records.

## Authority Model

- A repository path and commit SHA identify the canonical document revision.
- Supabase records must point to canonical content and must not silently supersede it.
- Search indexes, summaries, and embeddings are derived and rebuildable.
- Workflow state may be authoritative for an active run, but publication authority remains the approved GitHub commit.
- Every row belongs to a workspace and is protected by row-level security.

## Core Entities

| Entity | Purpose | Required fields |
| --- | --- | --- |
| documents | Stable identity and current lifecycle metadata | id, workspace_id, document_key, title, repository_path, owner_role, status, classification |
| document_versions | Immutable observation of a Git revision | id, document_id, commit_sha, content_hash, semantic_version, observed_at |
| document_sources | Provenance for claims and inputs | id, document_version_id, source_type, source_locator, retrieved_at, trust_state |
| document_relationships | Typed links between knowledge items | source_document_id, target_document_id, relationship_type, effective_at |
| review_requests | Review scope and routing | id, document_version_id, reviewer_role, risk_class, status, due_at |
| reviews | Reviewer findings and disposition | id, review_request_id, reviewer_id, decision, comments_ref, decided_at |
| approvals | Explicit authority decision | id, document_version_id, approver_id, authority_scope, decision, decided_at |
| validation_runs | Reproducible validation execution | id, document_version_id, ruleset_version, status, started_at, completed_at |
| validation_findings | Individual QA result | id, validation_run_id, rule_id, severity, location, status |
| publication_events | Publication and retirement evidence | id, document_version_id, event_type, actor_id, commit_sha, occurred_at |
| sync_checkpoints | Last processed repository state | workspace_id, repository_id, branch, last_commit_sha, processed_at |
| sync_events | Idempotent ingestion ledger | id, provider_event_id, event_type, commit_sha, status, attempts |
| sync_conflicts | Drift or authority conflict | id, document_id, canonical_hash, indexed_hash, severity, resolution_status |
| knowledge_index_entries | Structured discovery record | document_version_id, terms, summary, source_commit_sha, generated_at |
| embedding_refs | Reference to derived vector data | document_version_id, chunk_key, model_id, content_hash, storage_ref |

## Identifiers and Constraints

- Primary keys use UUIDs generated by the database.
- document_key is stable across moves and must be unique within a workspace.
- repository_path is unique for active documents within a repository and branch.
- document_versions are unique by document_id and commit_sha.
- sync_events are unique by provider_event_id and handler version.
- Relationship types use the controlled values governs, implements, depends_on, references, supersedes, validates, derived_from, and owned_by.
- Status values align with Documentation Standards: Draft, Proposed, Baseline, Approved, Active, Deprecated, and Retired.
- Content hashes use one documented algorithm over normalized UTF-8 source bytes.

## Relationships and Lifecycle

A document has many immutable versions. Each version may have sources, validation runs, reviews, approvals, publication events, index entries, and embedding references. Relationships attach to stable document identities unless a version-specific dependency is required. Retiring a document preserves its versions and audit trail while removing or demoting derived discovery entries.

## Data Classification and Access

Classification propagates from documents to versions, excerpts, findings, summaries, and embeddings. Policies must enforce workspace membership and role-based permissions. Authors may create drafts and workflow records. Reviewers may record decisions within assigned scope. Only authorized publishing identities may record successful publication. Service-role credentials remain server-side and are never exposed to browsers or document content.

Tables exposed through the Supabase Data API must have row-level security enabled. Policies must combine the target role with workspace and ownership or assignment predicates. Update policies require both visibility and post-update checks.

## Integrity Rules

- A published or approved version must reference a commit SHA and matching content hash.
- An approval cannot target a version with unresolved blocking validation findings.
- Derived entries must store the source commit and content hash used to create them.
- A supersedes relationship requires the replacement document to be Approved or Active before retirement completes.
- Audit and publication events are append-only.
- Hard deletion requires an approved retention, privacy, or security action and must propagate to derived stores.

## Indexing and Retention

Indexes prioritize Approved and Active documents, then Baseline documents. Drafts remain segregated. Chunking must preserve document and heading identifiers. Embeddings store references rather than secret or Restricted content unless governance explicitly approves the use case. All derived data must be reproducible from allowed canonical sources.

## Migration Requirements

The schema is delivered through ordered Supabase migrations. Each migration must define constraints, indexes, row-level security, grants, rollback or forward-recovery guidance, and verification queries. Seed data may establish controlled statuses, relationship types, and validation rules, but must not include production documents or credentials.

## Acceptance Criteria

- Every canonical document maps to one stable document record and one or more immutable versions.
- Provenance, validation, review, approval, and publication are traceable.
- Workspace isolation and least privilege are enforced.
- Conflicts cannot silently change canonical authority.
- Derived indexes can be deleted and rebuilt from GitHub.
- Retention and deletion actions cover derived artifacts.
